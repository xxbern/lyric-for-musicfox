# Lyric For Music 项目体检报告

本报告面向后续接手重构工作的 Subagent，目的是把当前代码库中需要解决的问题描述清楚，并讲清楚每个问题应该怎么解决（仅描述思路，不写代码、不排期、不分阶段）。

阅读对象：负责实施重构的 Worker Agent 和 Reviewer Agent。请先通读本报告，再开始动手。

## 问题一：字体加载导致的内存膨胀

**问题描述**

进程启动后，仅"准备好主窗口"这一个动作就要消耗约 125MB 物理内存，远超 `req.md` 规定的 50MB 上限。其中字体相关的开销占了大头，分三层叠加：

第一层，`fontdb` 这个第三方库的作用是枚举操作系统上安装的所有字体。它在代码里被调用了 5 次，分别在主进程启动、主进程 GUI 主循环、设置进程启动、设置页保存按钮、设置页关闭确认弹窗这五个地方。每次调用都会把 `C:\Windows\Fonts` 下几百个字体文件全部扫一遍，过程中分配大量临时小对象。Windows 默认的堆分配器有个特点：即便这些小对象最终被释放，它也不会主动把内存页归还给操作系统，于是形成大量堆碎片。在任务管理器眼里，进程内存就是这种"账面占用"，每次扫描大约贡献 15-30MB 常驻内存。

第二层，用户配置的中文字体（默认微软雅黑，对应的 `msyh.ttc` 文件大小约 35-48MB）被完整读取后复制成 `Vec<u8>`，再塞给 GUI 框架的 `egui::FontData::from_owned()`。egui 内部解析字体时**不会丢弃原始字节**——它既要保留原始的 `Vec<u8>`，又要保留解析后的字形轮廓数据结构，两份数据同时存在。仅"加载微软雅黑"这一个动作就吃掉约 70MB（一半原始字节、一半解析结果）。

第三层，`egui::FontDefinitions::default()` 不是空的，它内置了 Hack、Ubuntu-Light、NotoEmoji、EmojiOne 等英文和 Emoji 字体。对于一个只显示中文歌词的应用来说，这些完全多余，仍然驻留约 5-10MB。

**如何解决**

把字体相关的所有逻辑收敛到一个独立模块里，让它成为整个项目唯一接触字体的地方。具体讲三件事：

只扫描一次系统字体目录。在程序的整个生命周期里，`fontdb` 的扫描结果应该是共享的，而不是每次用到都重新扫描。借助 `OnceLock` 机制保证 `fontdb::Database` 实例只在第一次被访问时创建，之后所有调用都通过同一个引用访问。这样无论代码里写多少次"列出系统字体"，底层只会真正扫描一次。

原始字体字节用完就释放，不再长期缓存。egui 在调用 `set_fonts` 完成、字体数据进入 GPU 纹理图集之后，原始字节就没有用了。让 `Vec<u8>` 在调用后立即离开作用域，Rust 会自动回收它。如果有"换字体"需求，可以用 `Arc<Vec<u8>>` 这种零拷贝引用类型，让 egui 读取数据但不需要复制。只对当前字体家族做短期缓存，不要缓存所有曾经加载过的字体。

丢弃 egui 默认字体。改用 `egui::FontDefinitions::empty()`（空的），只往里面塞用户配置的那一种中文字体，并只注册到 egui 的"比例字体家族"这一个抽象分类里。这样 egui 内部就不会有 Hack、Ubuntu-Light、Emoji 等默认字体的踪迹。

同时把 `window`、`settings`、`tray` 三个模块各自打开字体数据库的代码都收拢到这个统一的字体模块里。三个模块不需要知道字体是怎么加载的，只需要告诉字体服务"我需要某某字体的字节"，字体服务自己决定怎么扫描、怎么缓存、怎么释放。

**预期收益**：删除默认字体省 5-10MB，消除重复扫描省 15-20MB，释放原始字节省 30-40MB，合计可省 50-70MB，让内存回到 50MB 预算之内。

## 问题二：进程间通信协议在两处复制粘贴

**问题描述**

主进程和设置进程之间通过 Windows 命名管道通信。这套协议在三块代码里被重复实现：管道名字的拼接规则、`pos` 协议（一问一答，询问主进程窗口当前坐标）的请求和应答解析、`session_id`（Windows 会话标识）的获取逻辑。

具体表现：设置进程里有一份 `parse_pos_response`，主进程服务端里也有一份同样语义的解析代码；`format!(r"\\.\pipe\lyric-for-musicfox-{}-{}", base, session_id)` 这个模板字符串在 5 个地方出现；`get_session_id` 函数在 `pipe/windows_pipe.rs` 和 `settings/mod.rs` 各写一遍。

这意味着：以后如果想给协议加点东西（比如鉴权、加密、版本号），就得跨两个文件同步修改，极易遗漏。协议层也没有独立单元测试，因为解析代码和 Windows API 紧耦合，没法在 Linux CI 环境下验证。

**如何解决**

把协议相关的所有内容抽到一个独立的协议模块里，作为整个项目唯一接触"协议长什么样"的地方。这个模块提供三组能力：管道名字生成（传入"管道用途分类"和"会话标识"，返回完整管道路径）、消息编解码（把请求和应答抽象成枚举类型，提供编码成字节流和解码回枚举的方法）、会话标识获取（封装 Windows API 调用，统一对外暴露）。

调用方改造：所有原本自己拼接管道名字、自己解析应答、自己调 Windows API 获取 session_id 的地方，都改成调用协议模块提供的统一 API。

这样协议层不再依赖 Windows API（具体 Windows 调用下沉到平台层），可以在 Linux 上独立做单元测试。新增消息类型时只需要在协议模块里加一个枚举变体和一对编解码方法，不需要改动其他任何文件。

**预期收益**：消除约 150 行重复代码；协议层可独立单测；新增协议时改动点收敛到一处。

## 问题三：平台差异代码散落各处

**问题描述**

代码里需要区分"Windows 行为"和"非 Windows 行为"的地方很多——托盘、命名管道、进程互斥、单实例检测、窗口原生句柄操作。这些差异目前通过 `#[cfg(windows)]` 这种条件编译属性直接写在业务代码里，全项目约有 30 处。

问题是，业务逻辑（比如"启动托盘并接收点击事件"）和平台细节（"Windows 上用 tray-icon 库、Linux 上是个 noop"）混在同一个函数里。这样有三个坏处：第一，业务代码读起来到处是 cfg 标记，看不清主流程；第二，想给业务代码写单元测试时，无法在不打开真实 Windows API 的情况下 mock 掉托盘行为；第三，将来想加 macOS 支持时，得在十几个文件里分别加 cfg 分支。

**如何解决**

把所有平台相关的代码抽到一个独立的"平台适配层"目录里，在这个目录下按子系统（托盘、管道、互斥、窗口）划分，每个子系统提供一组 trait（接口契约），并分别为 Windows 和非 Windows 实现这套 trait。

业务代码通过 trait 调用平台能力。比如托盘模块定义 `TrayBackend` trait，里面声明"建立托盘"、"设置图标"、"轮询事件"这些抽象方法；Windows 实现里用 `tray-icon` 库实现这些方法，非 Windows 实现里写成 noop（什么都不做）。业务代码完全不出现 `#[cfg(windows)]`，它只跟 trait 打交道。

这样加新平台时（比如 macOS），只需要在平台适配层加一个新的实现文件，业务代码一行都不用改。

**预期收益**：`#[cfg(windows)]` 散布点从约 30 处收敛到平台层内部的 10 处以内；业务代码清爽可读；新增平台成本 = 1 个实现文件。

## 问题四：进程状态散落各处，封装失守

**问题描述**

整个进程共享三块状态：当前窗口配置（`Config`）、当前歌词显示状态（`LyricState`，包括当前歌词文本、播放状态、窗口位置等）、各种布尔信号（是否需要重新加载配置、是否正在拖动窗口、显示器是否发生变化）。

这三块状态目前各自用不同的并发原语保护：`Config` 通过 `Arc<Mutex<Option<Config>>>` 实现（一种延迟加载的配置容器）；`LyricState` 通过 `Arc<RwLock<LyricState>>` 实现（读写锁，允许多读单写）；布尔信号通过三个独立的 `Arc<AtomicBool>` 实现。三者作为三个独立参数被传给各个模块（UDP 接收线程、托盘线程、管道服务端、GUI 主线程）。

问题有几个：第一，调用方必须同时持有三个引用才能完整表达"读取数据+设置信号+接收新配置"的组合动作，三个引用的生命周期管理复杂；第二，GUI 主线程里有个 `LyricApp` 结构体，它有 25 多个 `pub`（公开）字段，几乎没有任何私有字段，这意味着任何模块都可以直接读写 `LyricApp` 的内部状态，编译期无法保证"哪些字段必须协同更新"这类不变式；第三，配置变更的"反向传递"模式（即由非 GUI 线程把新配置塞给 GUI 线程）通过 `Arc<Mutex<Option<Config>>>` 加 `AtomicBool` 双重表达（既要检查标志位又要取出值），存在冗余和遗漏风险。

**如何解决**

引入一个统一的"应用上下文"结构，把三块状态集中收纳。这个结构持有配置（用一种"读多写少，无锁读取"的并发容器包装，外部读配置时开销几乎为零）、歌词状态（仍用读写锁）、布尔信号集合（三个原子布尔集中放在一个 `Signals` 子结构里）、事件总线（详见下一个问题）。

整个进程通过一个 `Arc<AppContext>` 共享指针传递这个上下文，各模块持有这个指针的克隆。需要读取配置时调 `ctx.config()`，需要写入时调 `ctx.replace_config(new_cfg)`（内部自动广播事件）。布尔信号统一通过 `ctx.signals().needs_reload.store(...)` 访问，再也没有散落的独立 `Arc<AtomicBool>`。

GUI 主线程的 `LyricApp` 结构体重构：25+ 字段收敛到 5 个左右——`ctx`（共享状态引用）、`services`（各业务服务的句柄集合）、`scroll`（滚动状态）、`drag`（拖动状态）、`render_cache`（渲染缓存）。所有字段改为私有或包内可见，外部只能通过方法访问。这样编译期就能防止意外的状态不一致。

**预期收益**：状态访问从三参数简化为一参数；GUI 状态结构从 25+ 字段收敛到约 5 个；新增状态时只需在上下文结构里加字段，不必修改所有调用方；锁毒化恢复、配置反向传递等模式集中处理，避免分散遗漏。

## 问题五：跨模块"反向依赖"和消息类型不安全

**问题描述**

GUI 框架（egui）有一个全局上下文对象（代表"主窗口里那块画布"），理论上只能由 GUI 主线程访问。但当前代码里有一个全局静态变量 `EGUI_CTX`，让 UDP 接收线程、托盘事件线程、命名管道服务端都能直接拿到这个上下文并调用 `request_repaint()`（通知 GUI 立即重绘一帧）。

这是两个问题的叠加：其一是"反向依赖"——托盘模块和管道模块按理说应该是 GUI 模块的下游消费者，不应该反向伸手去拿 GUI 的内部细节；其二是"启动顺序隐式约定"——所有反向访问都依赖一个隐含假设："GUI 上下文一定在第一次反向访问之前初始化完毕"，但编译器并不知道这件事，如果启动顺序改了，可能出现"未初始化就访问"的运行时崩溃。

此外，进程里还有 3 处 `crossbeam_channel::unbounded()`（无界通道）调用。无界的意思是：发送方永远不会被阻塞、消息可以无限堆积。如果某个事件源突然高频发送（比如 UDP 因为某种 bug 变成 1000Hz 而不是 10Hz），通道会无限增长直到进程内存耗尽——这是经典的"内存炸弹"模式。

还有一个问题：托盘、管道、UDP 三个事件源各自用不同的并发原语向 GUI 传递信号，有的是布尔标志、有的是通道、有的是直接调全局变量。新增事件类型时只能继续追加字段或加新通道，缺乏统一的扩展点。

**如何解决**

引入一个类型化的事件总线，作为整个进程唯一的"跨模块异步消息通道"。所有需要通知 GUI 或其他模块发生的事情，都通过 `events.emit(SomeEvent::Variant { ... })` 发送，不再直接调 GUI 上下文的重绘方法。

事件总线用有界通道实现（`bounded(N)`），超过容量的事件按业务重要性丢弃（比如丢弃最旧或最新）。各模块按消息频率选择合理容量：主事件总线 256 条、UDP 通道 16 条、托盘通道 8 条、日志通道 1024 条。

GUI 主线程在每帧开头一次性 `while let Ok(event) = events_rx.try_recv()` 排空事件总线，根据事件类型决定后续动作——收到"请求重绘"事件就调 `ctx.request_repaint()`，收到"配置已重载"事件就触发字体重新加载，收到"歌词行到达"事件就触发渲染缓存失效。这样事件类型在编译期就是已知的（用枚举穷举），不会出现"某个事件类型没人监听导致静默丢失"的问题。

`EGUI_CTX` 全局静态变量删除。所有反向依赖都改成走事件总线。

**预期收益**：消除两处反向依赖（管道→GUI、托盘→GUI）；有界通道提供背压，杜绝内存炸弹；新增事件类型只需扩展枚举变体；调试时可一次性把事件流 dump 到日志便于排查。

## 问题六：业务逻辑和 UI 渲染纠缠在一起

**问题描述**

`window/mod.rs` 这个文件有 600 多行，混合了至少 8 种职责：字体加载、配置管理、显示器枚举与裁剪、托盘事件处理、拖动状态机、滚屏状态机、渲染缓存管理、stay-on-top 刷新。

这种"什么都往一个文件里塞"的结构有几个坏处：第一，业务逻辑（"配置改了应该怎么响应"）和 UI 细节（"用 egui 的哪个 API 画文字"）混在一起，读代码时需要在两个抽象层次之间反复切换；第二，无法单独测试业务逻辑——你想验证"配置改了之后字体是否会重新加载"，必须启动整个 GUI 框架，没法在隔离环境里跑单元测试；第三，业务改动（比如改字体回退策略）必须改这个超大文件，难以做 Code Review。

**如何解决**

把 8 种职责拆成独立的"业务服务"，每个服务是一个结构体，职责单一，可以独立构造、独立测试。具体讲：

字体服务负责所有字体相关逻辑：解析用户配置里的字体家族、决定回退到哪个字体、从字体数据库加载字节、应用到 GUI 框架。它对外暴露"解析并应用字体"这一个高级方法，业务层不需要关心内部细节。

配置服务负责配置的加载、保存、校验、重载。它持有配置文件的路径，对外暴露"加载或默认"、"原子保存"、"从磁盘重读"三个方法。配置变更时它通过事件总线通知其他服务，而不是直接调用其他服务的方法。

显示器服务负责显示器的枚举、窗口坐标的裁剪、DPI 缩放比的查询。它对外暴露"获取当前布局"、"裁剪窗口位置"两个方法。收到"显示器变化"事件时自动重新枚举。

位置服务负责窗口坐标的内存管理、拖动状态机的协调。它对外暴露"获取当前位置"、"处理指针输入"、"退出时落盘"三个方法。

窗口样式服务负责原生窗口句柄的样式操作：设置窗口穿透（`WS_EX_TRANSPARENT`，让锁定时鼠标穿透到下层）、刷新 stay-on-top（保持窗口置顶）。它持有原生窗口句柄的引用，对外暴露"应用锁定样式"、"刷新置顶"两个方法。

托盘服务负责托盘的完整生命周期：创建托盘、处理菜单点击、维护闪烁状态、发出用户动作。它对外暴露"轮询动作"和"设置闪烁"两个方法。

歌词服务负责 UDP 接收循环的启动和管理。

八个服务通过 `ServiceHandles` 结构聚合。`LyricApp` 只持有这个聚合，业务代码通过服务访问具体能力，而不是直接读写内部字段。

**预期收益**：`window/mod.rs` 从 600 多行降到约 250 行；每个服务可独立单元测试；业务改动影响面明确（只改对应服务）；新增业务能力只需新增服务，不必修改 `LyricApp`。

## 问题七：进程间通信的服务端/客户端混杂

**问题描述**

项目里通过 Windows 命名管道提供三类进程间通信：reload 管道（设置进程保存配置后通知主进程重新加载）、pos 管道（设置进程启动时询问主进程当前窗口坐标）、presence 管道（设置进程启动时如果已有实例，激活已存在的设置窗口而不是开新的）。

这三类通信的代码全部塞在一个 `pipe/windows_pipe.rs` 文件里（340 行），混合了 Windows API 调用（`CreateNamedPipeW`、`ConnectNamedPipe` 这些）、协议解析、会话标识获取、回调逻辑。文件里还有大量重复代码——三个子模块各自写了一遍"创建管道 → 等待连接 → 读请求 → 写应答 → 关闭"的完整流程，每一遍都略有不同但本质相同。

服务端的实现细节（怎么调用 Windows API）跟业务逻辑（"reload 信号来了应该触发配置重载"）混在一起，导致无法在 Linux CI 环境下验证协议正确性，也很难扩展新管道类型。

**如何解决**

把命名管道相关的代码拆成三层：平台层提供 trait（"管道服务端"接口、"管道客户端"接口），Windows 实现负责 Windows API 调用，非 Windows 实现是 noop；协议层（在前一个问题里已经抽出来）负责消息的编解码和管道名字生成；业务服务层负责"收到 reload 信号后触发配置重载"这类业务响应。

具体地，平台层定义三个 trait——管道服务端（启动监听线程、停止监听）、管道客户端（发送请求并接收应答）、管道工具（管道名字编码等）。Windows 实现里封装 `CreateNamedPipeW` 等 API 调用，业务服务层不接触 Windows API。

业务服务层每个管道类型一个文件：`reload.rs` 负责"设置进程保存后通知主进程"这个动作的完整流程，包括构造请求字节、连接管道、发送请求、接收应答；`pos.rs` 负责"设置进程询问主进程当前位置"和"主进程响应这个询问"两件事；`presence.rs` 负责"检测已存在的设置窗口并激活"。

原来的 `pipe/windows_pipe.rs` 文件拆掉——Windows API 部分去平台层，业务部分去服务层，协议部分去协议层。

**预期收益**：服务端代码从 340 行降到约 200 行（平台层实现）+ 业务层约 50 行（reload + pos + presence 各一个文件）；新增管道类型只需新增一个业务文件；协议层和平台层可独立测试。

## 问题八：全局静态可变状态散落

**问题描述**

进程里有几个全局静态可变状态：`SharedSignals` 结构（包含三个 `Arc<AtomicBool>` 的拼装，分别表示"需要重载配置"、"正在拖动窗口"、"显示器发生变化"）；`DISPLAY_CHANGED_EVENT` 静态布尔（显示器变化事件的另一种表达，跟 `SharedSignals.display_changed` 是同一个东西，写了两遍）；`EGUI_CTX` 静态上下文（GUI 全局状态，已在问题五描述）；`OUTBOUND_SOCKET` 静态 UDP 套接字（用于发送命令给音乐播放器）。

这些全局状态有几个问题：第一，编译期无法追踪"谁在什么时候改了它"——任何模块都可以 `.store()` 一个值；第二，同一概念有两种表达（比如 `DISPLAY_CHANGED_EVENT` 和 `SharedSignals.display_changed` 是同一个状态），存在数据不一致风险；第三，测试时无法隔离——单测启动时这些静态状态已经被污染，无法获得干净的初始环境。

**如何解决**

把所有全局静态状态收拢到统一的应用上下文结构里（参见问题四）。`SharedSignals` 变成 `AppContext::Signals`，三个原子布尔集中在一个子结构里持有；`DISPLAY_CHANGED_EVENT` 删除，统一走 `signals.display_changed`；`EGUI_CTX` 删除，统一走事件总线（参见问题五）；`OUTBOUND_SOCKET` 保留为 UDP 命令模块内部的私有静态单例（这是合理的——单进程内同一 UDP 套接字复用是惯用做法）。

所有访问全局状态的代码改成通过上下文结构的方法访问。这样测试时可以通过构造新的上下文实例获得干净的初始环境。

**预期收益**：消除约 4 处全局可变状态；同一概念不再有重复表达；测试可获得隔离环境。

## 问题九：GUI 主线程的状态结构字段过多且全部公开

**问题描述**

`window/mod.rs` 里的 `LyricApp` 结构体有 25 多个公开字段——配置、状态、信号、新配置引用、托盘命令接收器、上次显示检查时间、每像素缩放比、滚动状态、解析后的字体家族名、上次帧时间、HWND、拖动状态、hit-test 应用标志、字体应用标志、9 个渲染缓存字段、stay-on-top 刷新时间……几乎所有的内部状态都是 `pub` 的。

问题有几个：第一，外部模块（包括其他模块的测试）可以直接读写这些字段，绕过了结构体的封装——比如 `cached_galley` 和它旁边的 8 个 `cached_text` / `cached_bold` / `cached_italic` 等字段必须协同更新（只要其中一个变了就要重排），但编译器不知道这件事；第二，单测时无法构造"最小化 `LyricApp`"来测试渲染缓存逻辑——你必须构造一个包含所有 25 个字段的结构体，但其中很多字段对当前测试毫无意义；第三，字段关系完全靠人工保证，没有文档说明"修改 X 时必须同时修改 Y"，新人接手时极易踩坑。

**如何解决**

按职责把 25 个字段收敛到约 5 个子结构，每个子结构有自己的字段，但对外提供有意义的命名方法：

`ctx` 字段：共享应用上下文引用（参见问题四），业务数据都在里面。

`services` 字段：业务服务集合（参见问题六），每个服务对应一类职责。

`render_cache` 字段：把原来散落的 9 个 `cached_*` 字段封装成一个子结构，对外提供 `needs_relayout(&snapshot, ppp) -> bool` 和 `refresh(&mut self, painter, snapshot, ppp)` 两个方法。这样"判断是否需要重排"和"执行重排"是有命名意义的操作，而不是"读 9 个字段手动拼条件 + 写 9 个字段手动同步"。

`scroll` 字段和 `drag` 字段：已经是独立子结构（`ScrollState` 和 `DragState`），保持不变。

所有字段从 `pub` 改为 `pub(crate)`（仅同包可见）或完全私有。外部只能通过方法访问，方法里有命名清晰的不变式保证。

**预期收益**：`LyricApp` 字段从 25+ 收敛到约 5 个；渲染缓存逻辑可独立测试（构造一个最小化 `RenderCache` 实例即可）；字段协同更新关系由类型系统保护，编译期就能防止遗漏。

## 验证与质量保证的总体要求

所有上述改动完成后，需要做以下验证：

第一，构建验证。每次阶段性重构完成后必须用 `cargo build --target x86_64-pc-windows-gnu` 重新构建 Windows 可执行文件，确保交叉编译通过。

第二，PE 资源完整性验证。用 `objdump -p target/x86_64-pc-windows-gnu/debug/lyric-for-musicfox.exe | grep -A 5 "Resource Directory"` 检查产物中的 PE 资源段，确保 `assets/icon.rc` 嵌入逻辑没有被破坏。

第三，内存验证。在 Windows 上运行二进制，用任务管理器观察"工作集（内存）"列，启动后 5 秒、无任何操作的稳态值应该回到 50MB 左右。

第四，单元测试覆盖率。每个新拆出的模块（字体、协议、平台、服务）应该独立可测，整体覆盖率应该显著提升。

第五，集成测试。原有的 `cargo test`（包含窗口、UDP、设置、配置等所有测试）必须继续通过；托盘图标显示、设置页保存触发主进程重载、设置进程查询主进程位置等关键路径必须有手动验收项。
